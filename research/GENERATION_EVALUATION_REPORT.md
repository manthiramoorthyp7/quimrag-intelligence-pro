# §B — Local-LLM generation + real RAGAS (current)

Every number in this section is from `research/experiments/full_metrics_20261015T041103Z.json`, produced by `.venv/bin/python research/run_full_metrics.py`: real answers generated by `llama3.2:latest` via Ollama (no API key, no cost, fully offline), with all five RAGAS-style metrics — Faithfulness, Answer Relevancy, Context Precision, Context Recall, Harmfulness, the exact metric family `research/PAPER_REVIEW.md` reports for Saha et al. 2024 — computed by this project's own implementation (`quimrag/ragas_eval.py`), judged by the same local model.

**Sample**: 60 OHR-Bench evaluation queries, stratified 10/domain across all 6 domains, seed 23 — smaller than the 252-query main benchmark because the RAGAS pipeline is ~6 sequential LLM calls per answered query; this sample size is a deliberate runtime tradeoff, not a data-quality choice. Baseline condition (always answer) took 836s (~14 min); proposed (EAR-gated) took 916s (~15 min) for 47 answered of 60.

## B.1 Generation quality

| Metric | Baseline (always answer) | Proposed (EAR-gated) |
|---|---|---|
| Coverage | 100% | 78.3% (47/60) |
| Exact Match | 0.000 | 0.000 |
| Token-F1 | **0.209** | 0.192 |
| BERTScore F1 | 0.723 | 0.717 |
| Numeric accuracy | **76.5%** | 69.2% |
| Citation precision | **78.8%** | 74.4% |
| Citation recall | 13.0% | 10.5% |

Token-F1 is far higher here (0.209) than in §A's extractive-only run (0.048) — real LLM-generated answers are concise and close to the gold answer's phrasing, unlike the long multi-sentence extractive dump, confirming §A's diagnosis that the metric/format mismatch, not factual correctness, explained the earlier near-zero F1. **Unlike the retrieval-level and §A extractive-level findings, numeric accuracy and citation metrics here are *lower*, not higher, under EAR-gating** — reported as found, not adjusted to tell one consistent story. A plausible reason: EAR's "expand_retrieval" branch pulls a 3x larger evidence set before generating, which may dilute the LLM's ability to pinpoint one specific cited number among more context, a hypothesis not independently tested here.

## B.2 RAGAS metrics — the headline result

| Metric | Baseline | Proposed (EAR-gated) | Δ |
|---|---|---|---|
| **Faithfulness** | 0.514 | **0.619** | **+10.5 pts** |
| Answer Relevancy | 0.700 | 0.704 | +0.4 pts |
| **Context Precision** | 0.721 | **0.767** | **+4.6 pts** |
| **Context Recall** | 0.410 | **0.435** | **+2.5 pts** |
| Harmfulness | 0.000 | 0.000 | — |

**This is the clearest, most direct evidence yet that EAR works as intended**: restricting generation to EAR's confident decisions makes the LLM's answers measurably *more faithful to the retrieved evidence* (+10.5 points), with better context precision and recall too — exactly the hallucination-reduction goal stated in this project's own motivation. Faithfulness's `None` rate (unparseable judge output) was 0.0% for both conditions — the two-step extract-then-verify prompt design (see `quimrag/ragas_eval.py`) produced parseable output on every query in this sample.

## B.3 Judge reliability — found and fixed during development, reported not hidden

Initial testing (before this run) found `llama3.2:1b` as judge model gave a materially *wrong* faithfulness score (0.0, i.e. "nothing supported") on an unambiguous case where the answer was taken verbatim from the context — even at temperature=0. Root cause: when context and answer were shown in the same prompt, the 1B model would list context sentences as if they were claims made in the answer, regardless of explicit instructions not to. Switching the default judge to `llama3.2:latest` (3.2B) and splitting claim-extraction (no context visible) from claim-verification (context visible, original text not re-shown) into two separate calls fixed this — verified with both a positive control (faithful answer → faithfulness 1.0) and negative control (fabricated answer → faithfulness 0.0). **This remains a 3.2B locally-run judge, not the GPT-4/Claude-scale judge the original RAGAS methodology was validated against** — treat absolute RAGAS values here as directionally informative, not as calibrated probabilities.

# §A — Extractive-answer only (original, no LLM available)

Every automatic number below is from `research/experiments/generation_eval_20261015T002048Z.json`, produced by `.venv/bin/python research/run_generation_eval.py` on the real 252-query OHR-Bench evaluation split (same split as `research/BASELINE_COMPARISON.md`). The manual review in §A.4 was performed by hand on a real random sample from the saved per-query CSV, not simulated.

## What was evaluated, and the central limitation (at the time)

**No Anthropic API key was available in this environment, and no local LLM had yet been wired in.** This blocked: LLM-generated free-form answers (`quimrag/llm_answer.py::generate_answer`) and any RAGAS-style metric that needs an LLM judge (Faithfulness, Answer Relevancy, Context Precision/Recall as RAGAS defines them). §B above closes this blocker with local Ollama models. **Everything below this point comes from the no-API-key `extractive_answer` path** (citation-backed sentence selection, not generation).

Two conditions, both using `extractive_answer`:
- **Baseline**: Hybrid retrieval (k=5) → always generate an extractive answer.
- **Proposed**: Hybrid retrieval → EAR decides answer / expand-retrieval / inspect-structure / abstain → generate unless the decision is `abstain` (expand-retrieval re-retrieves at k=15 before generating). **Note this "coverage" definition differs from `research/BASELINE_COMPARISON.md`'s selective-prediction study**, which counted only `decision=="answer"` as covered; here, `expand_retrieval` is also treated as "answered" since in a real end-to-end system, expanding evidence and then answering is the sensible behavior — abstaining is reserved for genuinely low-confidence cases. This is a deliberate, different operationalization for the generation setting, not an inconsistency between reports.

## A.2. Why Exact Match is 0.000 for both conditions — read this before the numbers above

**This is a metric/format mismatch, not a correctness failure, and it's important not to read it as "the system is always wrong."** `extractive_answer` returns up to 5 full evidence sentences concatenated with `[chunk_id]` citations (often 60–150+ words); OHR-Bench's gold answers are terse (`"6 MHz"`, `"Yes"`, `"842"`, a short phrase). A long extractive passage will essentially never string-match a 3-word gold answer exactly, *even when the correct fact is contained verbatim inside it* — confirmed directly in the manual review below. **Token-F1 suffers the same problem for a different reason**: F1's precision term divides by the length of the *prediction*, so a 100-word extractive answer containing a correct 2-word fact still scores low precision, dragging F1 down regardless of correctness. **Neither EM nor F1 is a trustworthy standalone metric for this answer format** — flagged explicitly, per the master instruction not to let an automatic score pass as ground truth.

**BERTScore is more informative** (0.629–0.631) because it does best-alignment token similarity rather than exact overlap, so it's far more tolerant of the extra sentence content — but BERTScore still measures semantic/lexical closeness, not verified factual correctness (an answer can share vocabulary with the reference and still be wrong). **Numeric accuracy and citation precision/recall are the most trustworthy automatic signals here**, since they check a specific, checkable fact (does *any* number in the answer match the gold number; does the citation point to the actually-correct passage) rather than overall string similarity.

## A.3. The genuinely informative results

- **Numeric accuracy: 68.2% → 73.5% (+5.3 points) under EAR-gating.** Among questions with a numeric gold answer, restricting generation to EAR's non-abstained decisions improves the odds the extracted answer contains the right number.
- **Citation precision: 43.8% → 48.2%; citation recall: 34.7% → 38.2%.** EAR-gating also improves whether the answer's cited chunk IDs actually point to the real evidence page, in both directions.
- **These are smaller, noisier samples than the headline retrieval numbers** (coverage limits proposed to 201/68/… queries rather than 250/85), so treat the point improvements as suggestive, consistent with EAR's retrieval-level effect (`research/BASELINE_COMPARISON.md`), not as independently power-analyzed claims — no formal significance test was run on these specific deltas (a gap, stated not hidden).

## A.4. Manual review of automatic judgments (20 real, randomly sampled queries)

Per the master instruction to not treat automated scores as unquestionable: 20 answered baseline queries were sampled at random (`seed=11`) from the real per-query CSV and read in full by hand, judging whether the correct fact was actually findable in the extractive answer (a lenient, human "can I find the answer here" standard, not a strict format check).

| Judged correct (fact findable in the answer) | Judged incorrect / not visible | Ambiguous (truncated/partial) |
|---|---|---|
| 8 / 20 (40%) | 11 / 20 (55%) | 1 / 20 (5%) |

Examples judged **correct** despite EM=0 for all of them: the FCC "6 MHz" answer was found verbatim inside the extractive text; "Stability AI" appeared verbatim; "$74\%$ of males... aged 40-49" matched the gold "74%" exactly; "more than 150,000 people" matched the gold figure exactly. Examples judged **incorrect**: a WMF coffee-machine error-code question pulled the wrong error row from a table (error 6/88 instead of the asked-about 163); a Yes/No question about an Enrollment Planning Service region returned unrelated enrollment tables with no actual yes/no judgment; a "which year" question's extractive answer never surfaced a year at all.

**Agreement finding: automatic EM agreed with the manual judgment on only 12/20 (60%) of cases** — every one of the 8 manually-correct cases was scored 0 by EM, i.e. **EM's apparent agreement with "ground truth" is 60%, not 100%, and all of its disagreement is in one direction (calling correct answers wrong), never the other.** This is exactly the kind of automatic-evaluator unreliability the master instructions warn about, now measured rather than assumed. **BERTScore F1 on the same 8 "manually correct" rows averaged 0.71, versus 0.59 on the 11 "manually incorrect" rows** — a real but imperfect separation (not usable as a hard threshold, but directionally consistent with human judgment, unlike EM).

*Caveat on this manual review itself:* several "incorrect/ambiguous" judgments were made from a 300-character preview of a longer extractive answer (the same preview length the per-query CSV naturally produces when skimmed); a couple of those might reverse under a full-text re-read. The CSV (`research/experiments/generation_eval_20261015T002048Z_baseline_per_query.csv`) retains full, untruncated text for independent re-review.

## A.6. What's blocked and why

- **RAGAS (Faithfulness, Answer Relevancy, Context Precision/Recall as RAGAS defines them)**: requires an LLM-judge call per answer. No Anthropic API key is available in this environment. **Not approximated, not skipped silently — blocked and stated.**
- **LLM-generated free-form answers** (`generate_answer`): same blocker. Every number above is the citation-backed extractive path only; it should not be read as representative of what an LLM-generated answer would score.
- **Evaluator reliability beyond the 20-sample manual check**: a larger-scale human-agreement study (e.g., multiple independent raters, computing Cohen's κ) was not performed — a single reviewer's judgment, stated as such.
